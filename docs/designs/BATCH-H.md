## 1. Decisions

**H1. Protection is read-merge-write** (audit G2, G3). `github_protection_set(changes)` reads the current protection, applies
only the named changes, sends the full object, reads back and compares every key; the preview lists each change as
"before → after" and every protection that stays. `github_protection_set_required_checks(add[], remove[])` uses the dedicated
required-checks endpoints and keeps the rest. No defaults are ever invented.

**H2. Rulesets are the recommended way** (GitHub's current model; Chris's repositories already use them — Appliance Desk
requires `ci` by ruleset). `github_ruleset_save` for updates also reads, merges and writes; the preview explains each rule in
words ("Pushes to main must have the `ci` check green", "Force pushes blocked", "Bypass: none"). Adding a **bypass actor**
is access-widening. `github_ruleset_list_rule_suites` answers "why was my push blocked?".

**H3. Webhook secrets are generated by the server** (audit G14): `github_webhook_save` creates a 32-byte random secret, sends it
to GitHub, and shows it once on the setup page; `github_webhook_rotate_secret` replaces it the same way. Target URLs must be
HTTPS and public (same SSRF rule as V-4). `github_webhook_list_deliveries` returns status, event, duration; a single delivery's
payload is capped and handled.

**H4. Access changes are explicit.** `github_collab_add` previews the permission before and after and notifies (M);
`github_deploykey_add` takes a **public** key only (a private key pasted by mistake is detected by its header and refused
without echoing it), and `read_only: false` is access-widening and production.

**H5. Security features may cost money.** On a **private** repository, turning on Advanced Security, Code Security or
Secret Protection is `$` (B-4; price per active committer from `src/github/prices.js`, verified in O-4 §0); on public
repositories those features are free and only production. Turning a security feature **off** is production and says what
protection is lost.

**H6. Alerts never leak secrets.** `github_security_get_alert` for secret scanning returns type, location, validity and state;
the `secret` field is removed before shaping (B-5 also hides it). `github_security_update_alert` requires a reason when
dismissing (`false_positive`, `wont_fix`, `used_in_tests`, …) and notes it in the change log.

**H7. Actions settings are production.** `github_actions_set_settings` covers allowed actions, default `GITHUB_TOKEN`
permissions (read/write, can approve PRs), fork-PR contributor approval, artifact/log retention; read-merge-write.

## 4. Work units

### H-1 — Branch protection and rulesets (M, medium effort)
Tests: changing one protection key keeps every other key (audit G2 regression); conversation resolution can be turned off
(G3 regression); ruleset update merges; bypass actor addition is access-widening; plain-words preview fixture.
### H-2 — Webhooks (M, medium effort)
Tests: no tool accepts a secret argument (schema test); secret shown once; HTTP or private URL refused; redeliver is
production when the hook is on a production repository; delivery payload capped.
### H-3 — Collaborators and deploy keys (S)
Tests: preview shows before/after permission; private key pasted → refused without echo; write deploy key needs a
production connection.
### H-4 — Security features, alerts, Actions settings (M)
Tests: paid feature on a private repo is `$` and refused at the $0 limit; free on public; secret-scanning `secret` never
in any result (key-scan + field test); dismiss without reason refused; settings read-merge-write.
