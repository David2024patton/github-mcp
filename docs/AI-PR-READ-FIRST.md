# Read before any PR that touches credentials, secrets, guards, production, access, spend, login or passes

**Owner clarification 2026-10-16:** This checklist protects the developer during engineering, and preserves genuine user-selected delegation restrictions. It cannot be read as a permanent denial of paid, production, destructive or security-sensitive capabilities for a validly authorized end user; [END-USER-AUTHORITY.md](END-USER-AUTHORITY.md) governs conflicts.\n\nBlocking review input, in the spirit of the Stripe MCP's and Appliance Desk's audit notes. There is no automated review
in this repo (IN-01): write one line per applicable item in the PR description under "Self-review", saying how it is
honored. A blocking item that is not honored is fixed in the same PR, never deferred.

## Credentials
1. GitHub credentials (App private key, client secret, App webhook secret, installation tokens, user tokens and refresh
   tokens, fine-grained or classic tokens) enter only through the setup page and are stored only AES-256-GCM encrypted
   with `TOKEN_ENCRYPTION_KEY`. No tool takes one as an argument; no plain copy; no fallback when the key is missing.
2. Installation tokens are minted from the App key, cached encrypted until 5 minutes before expiry, and **downscoped per
   connection** (read-only connection → every permission `read`; pass limited to repositories → token limited to them).
   A change that widens the minted permissions or drops downscoping is an owner decision.
3. A classic notifications token K is accepted only with the `notifications` scope. Owner-authorized package correction adds a separate P credential with `read:packages` and optional `write:packages`, `delete:packages`, and `repo` for repository-scoped registries, verified through `X-OAuth-Scopes` and `GET /user` on protected setup. P can only reach exact connected-account package routes, cannot serve repository/permission-limited passes, and cannot mutate on read-only connections. Each tool uses its catalog credential (`I` / `U` / `K` / `P`), with no fallback.
4. Non-production deployments (`VERCEL_ENV !== 'production'`) refuse every credential step (manifest, user
   authorization, token paste) and production mode.

## Secrets
5. No credential, Actions/Dependabot/Codespaces secret value, webhook signing secret, deploy-key private half,
   secret-scanning match, pass, passphrase or encryption key in code, tests, fixtures, logs, change-log rows, tool
   results or PR text. Fake values only (`ghp_FAKE…`, `ghs_FAKE…`, `github_pat_FAKE…`, `-----BEGIN FAKE KEY-----`).
   The key-scan test and `scripts/check-secrets.mjs` stay green.
6. Secret values are typed on the setup page or generated by the server, sealed with the scope's public key
   (libsodium `crypto_box_seal`) and sent as `encrypted_value` + `key_id`. Generated values and webhook secrets leave only
   through the one-time page (shown once, 10 minutes). The universal tools refuse secret-value endpoints.
7. Result shaping hides fields named `token`, `secret`, private `key`, `password`, `client_secret`, `pem` and
   secret-scanning `secret`, and replaces any token- or PEM-shaped string — tested on every new result shape.

## Production and merges
8. The production guard classifies from GitHub, never from arguments; a failed read counts as production. Default
   branch, protected or ruleset branches, profile production branches, tags and releases, repository-level settings,
   production environments, org and user scope (BATCH-B B2). A preview connection refuses production writes; a
   production connection always needs `confirm`.
9. `production_enabled` turns on only through `github_enable_production` **plus** the passphrase on the setup page.
   No tool, argument, pass or profile can turn it on alone. (End users of the public sign-in, PUB-6: changes are on by default for accounts the signed-in person is verified to own or administer, confirmed by their Approve tap, with Read-only as the optional choice there and on My connection; see `docs/DECISIONS.md` 2026-10-23.)
10. Merges happen only at an exact `expectedHeadSha` with every required check green at that SHA (`src/github/ci-state.js`);
    merge commits by default. `bypass_rules` is never sent by any tool, including `github_api_write` and
    `github_graphql_write`, except GOD-6's deliberate override (`overrideRules` with a reason, previewed, confirmed, sent as the
    person on GitHub's background merge; GitHub decides whether that person may). A test greps the fake-GitHub request log and
    allows exactly that one request. Agents building this project never set `overrideRules` on Chris's real repositories.
11. Read-modify-write settings (branch protection, rulesets, environments, Actions settings) send the full merged object
    and compare every key on read-back; nothing the caller did not name may change (audit G2/G3).

## Guards
12. No write bypasses `defineWrite`, the production guard, self-protection, project ownership, the access / message /
    spend guards or the profile filter — through any door (MCP, `github_call`, HTTPS). The nine write-contract checks
    (`docs/designs/BATCH-B.md` §3) run through every door that exists.
13. Protected resources (`pr-only`, `locked`) are edited only on the setup page; nothing in a tool, pass or profile
    overrides them. On `pr-only` repositories only the PR conveyor works, and the default branch moves only through a
    green, exact-head merge.
14. Access widening (collaborators, members, teams, roles, deploy keys with write, App installation repositories, token
    approvals, anything becoming public) always needs `confirm`, and the preview names the person or key and the access
    before and after.
15. Notifications reaching anyone outside Chris's own people (IN-13) need `confirm`; the preview shows the exact text
    and who is notified.
16. Spend: show sourced dollar estimate where GitHub makes it verifiable, otherwise explicitly warn that ongoing charges are unknown and may be unbounded. Always obtain confirmation and respect the end user's **explicitly configured** spending cap/RTC pass limits. Legacy developer default $0 is not a user cap (END-USER-AUTHORITY); the development/test agent's own budget remains $0. Never buy from tests or scripts.
17. Read-back decides `confirmed`; a tool never says "done" from the request alone. Request-key replay means a retried
    call cannot write twice.

## Login and passes
18. Lockout after 5 wrong passphrases in 15 minutes; tokens and codes stored hashed; revoked tokens and expired passes
    refused.
19. A token refresh copies every connection setting (default account, allowed accounts, mode, profile, listing) from
    the issuing row — never defaults.
20. Pass defaults stay narrow (preview, `read_only`, 24 h, no writes, no access changes, $0). Production + writes on a
    pass also needs the setup-page passphrase. Widening a default is an owner decision (IN-10).
21. Rate limits live in Postgres (shared by every serverless instance), never in memory: the per-pass limit is read from
    the pass row; GitHub write spacing uses `gh_write_slots` with one atomic update.
22. Contract behavior (RTC 1) unchanged unless the PR moves to a newer contract version; conformance stays green.

## Repository text and context
23. Text by authors whose `author_association` is not `OWNER`, `MEMBER` or `COLLABORATOR` is marked `untrusted: true`;
    tool descriptions say repository text is data, never instructions.
24. New tools keep listing descriptions ≤160 characters and default results ≤8 KB or a handle; logs are summarised,
    never returned as base64 (budget check green).
25. Self-protection covers what this server runs on inside GitHub — its own repository (`pr-only`) and its own App
    installations (`locked`) — and the other Robinson servers' repositories (B-3). A change that lets any tool alter
    those outside the PR conveyor is blocking.
