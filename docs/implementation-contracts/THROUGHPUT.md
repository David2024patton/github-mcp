# Throughput contract — evidence-driven development without weaker gates
Aligned 2026-10-15; historical observations from 2026-10-12 retained; referenced by AGENTS, SESSION-START, PLAYBOOK and IMPLEMENTATION-DETAIL. This is execution guidance, not an approval to change designs or real GitHub resources.

## Observed bottlenecks (actual #60–#64)
- The pre-fix full unit job commonly occupied over 200 seconds after check/shapes completed in seconds. #60 post-merge unit ran about 233 seconds (23:43:27–23:47:20 UTC). Before: one `npm test` per CI run. After #65: two deterministic Vitest file shards in parallel; the aggregate `ci` still fails if either shard fails, with no excluded tests. Measure first exact-head run before claiming wall-time savings.
- #60 used unsupported `page` / `per_page` on GET user package versions. #62 initially declared `when-target` with catalog `C·D·Prod`; the exact checker requires `always`. #64 restore passed an explicitly undefined optional argument through dispatcher fixtures; corrected to omit it. These were preventable with pinned OpenAPI and tool-contract comparison before CI.
- A closer #64 baseline unit log identified `tests/unit/pulls-write.test.js` alone taking ~200.9 seconds. Two independent problems surfaced: the shared write-contract dispatcher omitted its fake-world sleep injection (fixed), **and** fake worlds did not register `GET /orgs/{org}/members`, causing repeatable fake `501` replies to an internal notification-classification read. Octokit's retry middleware then consumed real wall time. The first sleep-only fix did **not** reduce runtime (#65 unit shard still 222 seconds). #65 now provides a realistic `200` membership fixture by default; explicit `403` overrides and fail-closed permission tests remain. The real GitHub client keeps its 1-second write spacing, independently tested by `tests/unit/client.test.js` and `tests/db/write-slots.test.js`. Measure the next run before claiming a speedup.
- The #65 first CI cycle also failed because the new JIT card omitted the validator's literal `Drift check` words and the schema assertions hard-coded a 17-table/20-statement snapshot. The card README now names the required heading; schema tests derive counts from `SCHEMA_TABLES` while retaining explicit critical index assertions. A regression test confirms both dispatcher doors use the fake `sleep` and still reserve spaced write slots.
- #63 database job failed before test execution because the public ECR Docker image was throttled; the failed job rerun succeeded with no code change. Distinguish infrastructure failures from code failures using exact job logs; never weaken database assertions.
- Related Pages and package operations spanned #60–#64, each incurring an independent full CI/review/merge cycle. This made security review manageable, but future same-risk operations should be grouped *before* creating a PR.

## Default grouping and execution recipe
1. Reconcile exact current main, your open PRs, unresolved threads and CI first. Run `npm run task:brief -- V-1` for the immediate card (replace ID). Read its design heading, nearest working helper and the single needed recipe, not all documents.
2. Select related whole existing subsections for a usable bundle, normally averaging 2–5 subsections and 400–800 meaningful production lines. A card, module or API family is not an automatic publication boundary. Connected policy persistence and policy assessment/repair, for example, may share a bundle when the original approved scope, dependencies and migration proof support it. Keep each destructive/auth/spend boundary, credential, confirmation and denial independently enforced and tested. No 500/800-line ceiling or one-risk/one-migration quota applies; larger coherent outcomes are allowed when reliably reviewable. Split PRs only for a named concrete migration, dependency, safety or reviewability reason, and count the assembled bundle once. Never pad lines, invent tools or group unrelated work.
3. Before each new API operation run `node scripts/openapi-find.mjs --show "<METHOD /route>"`; record supported path/query/body fields and credential class on the card. Use `defineRead`, `defineGithubWrite`, `githubFor`, `productionReason`, and `runWriteContract` rather than new bypass paths.
4. Reuse a focused contract fixture for each risk area (real and fake SQL share one assertion body). For optional arguments, *omit* absent properties in dispatched fixtures, don't send undefined. Read GitHub API responses independently before reporting a write confirmed.
5. Validate an incremental slice with `npx vitest run tests/unit/<file>`, `npx eslint <files>`, then database/request-shape tests when touched. Before publishing the assembled outcome run `npm run check` and every applicable full suite. With no shell, use draft PR CI for the assembled bundle (or its justified delivery boundary), not each helper or small card; never push while its prior run is incomplete.
6. On failure capture all completed job logs, categorize `code / API shape / metadata / infrastructure`. Fix all code failures in one batch; rerun failed jobs only on clean infrastructure errors. Never poll identical pending checks repeatedly. Keep the specific branch/head/run/action in a ≤20-line progress note.
7. Finish the current PR: self-review the entire diff against `docs/AI-PR-READ-FIRST.md`; resolve threads; confirm exact-head `ci` success; merge with expected-head SHA. Then update STATUS, selected cards and work-index as merged, with measured CI timing when available. A delivery checkpoint or incidental fix does not satisfy the owner bundle target; continue the unfinished bundle before counting it.
