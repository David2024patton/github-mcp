## 1. The API surface (playbook step 1)

### 1.1 REST

- **Versioning.** Calendar versions sent in the `X-GitHub-Api-Version` header. Supported today: **`2026-03-10`** (latest,
  released 2026-03-10/12, the first calendar version with breaking changes) and `2022-11-28` (supported until at least
  2028-03-10). A request without the header gets `2022-11-28`. Each version is supported for 24 months after its
  successor ships. [S1][S2]
- **Decision: pin `2026-03-10`** (`docs/designs/BATCH-A.md` A7). Its 26 breaking changes [S3] that matter here:
  `rate` removed from `GET /rate_limit` (read `resources.core`); `merge_commit_sha` removed from pull request objects
  (read-back of a merge uses the merge response's `sha` and the base branch head instead); singular `assignee` removed
  (use `assignees`); `use_squash_pr_title_as_default` replaced by `squash_merge_commit_title`; **workflow dispatch now
  returns `200` with the run's ID and URLs** (Batch V and `actions_dispatch` rely on it); `has_downloads` removed;
  `DELETE /app/installations/{id}` returns `202`; submodules listed as `type: submodule`; 451 status for trade-control
  refusals on repo creation and membership changes (the error map handles it).
- **OpenAPI description.** `github/rest-api-description`, file
  `descriptions/api.github.com/api.github.com.2026-03-10.json` (OpenAPI 3.0.3, `info.version` 1.1.4, 12.9 MB, sha256
  `2b61199d…b376`) at commit `58b1e0c00b39b9e46c24dc4a0ba6a2669c90e9c1` (2026-10-10). A per-version file exists for
  both supported versions; a dereferenced copy and an OpenAPI 3.1 preview (`descriptions-next/`) also exist. MIT
  licence. [S4] A-4 vendors the bundled 2026-03-10 JSON and records URL, commit and checksum in `vendor/github-openapi/SOURCE.md`.
- **Size of the surface** (counted from that file today): **1,232 operations** — 644 GET, 588 writes of which 188 are
  DELETE; 38 marked deprecated; 50 categories. Largest: actions 208 (105 writes), orgs 129, repos 73, issues 61,
  codespaces 48, users 47, branches 38, apps 37, pulls 35, activity 34, teams 32, copilot 31, agents 30,
  copilot-spaces 28, packages 27, projects 26, dependabot 25, code-scanning 25.
- **GitHub's own operation metadata** (`x-github`) used by this plan: `category`/`subcategory` (areas), 
  `enabledForGitHubApps`, `githubCloudOnly`, **`triggersNotification` (25 operations — creating issues, comments, PRs,
  reviews, review requests, merges, releases, collaborator invitations, org invitations)**, `deprecationDate`/`removalDate`
  (security-manager endpoints removed 2026-01-01; the old repo-import API removed 2024-04-12; Classroom endpoints
  2026-08-28; the SBOM export 2026-11-13).
- **New since the old toolkit was written** (all present at 2026-03-10): pull request **stacks** (`/repos/{o}/{r}/stacks`),
  **`merge-async`** (merge in the background with `merge_action`, plus a **`bypass_rules`** flag this server must never
  send), sub-issues, issue dependencies and issue fields, issue types, org **billing budgets** and the enhanced billing
  usage reports (`/organizations/{org}/settings/billing/usage|usage/summary|premium_request/usage|ai_credit/usage` and the
  `/users/{username}/…` equivalents), immutable releases settings, organization roles, fine-grained token requests and
  approvals, Copilot cloud-agent permissions, agent secrets/variables, Copilot Spaces, agent tasks, Actions policies,
  hosted runners with custom images.
- **Gone or never in the free/Team description:** the **org audit log REST endpoint** (Enterprise Cloud only — not in
  the api.github.com description), **required workflows** (`/orgs/{org}/required_workflows` — no longer exists; rulesets
  replaced them), custom repository roles (Enterprise Cloud description only).

### 1.2 GraphQL

- Public schema `src/graphql/data/fpt/schema.docs.graphql` in `github/docs` at commit
  `be38ec5d78e24172587e61b3c6ff40ace1865c71` (2026-10-09; 1.56 MB, sha256 `3ed09565…8d42`), also served at
  `https://docs.github.com/public/fpt/schema.docs.graphql`. **246 mutations, 32 root query fields.** [S5]
- GraphQL-only operations this server needs: `resolveReviewThread`/`unresolveReviewThread`, review threads with
  resolved state, `enablePullRequestAutoMerge`/`disable…`, `enqueuePullRequest`, `markPullRequestReadyForReview`/
  `convertPullRequestToDraft`, `createCommitOnBranch` (multi-file signed commits with `expectedHeadOid`), `updateRefs`
  (`beforeOid` compare-and-swap), discussions (`createDiscussion`, `addDiscussionComment`), Projects v2 field updates,
  `transferIssue`. All verified present in the schema today.
- Limits [S7]: 5,000 points/hour for users, installations 5,000 + 50/repo and 50/user beyond 20 each, capped at 12,500;
  `first`/`last` 1–100 on every connection; ≤500,000 nodes per call; 10-second timeout (timeouts cost extra points);
  secondary 2,000 points/minute, mutations cost 5.

### 1.3 Rate limits and good behaviour (REST) [S6][S8]

- Primary: 5,000/hour for a user or token; installation tokens 5,000 + 50/repo + 50/user beyond 20, max 12,500
  (15,000 on Enterprise Cloud); `GITHUB_TOKEN` 1,000/repo; OAuth token requests 2,000/hour per app.
- Secondary: 100 concurrent requests (shared with GraphQL); 900 points/minute per endpoint (GET 1, writes 5);
  90 s CPU per 60 s; **content creation about 80/minute and 500/hour**; may change without notice.
- When limited: 403 or 429; honour `retry-after`; if `x-ratelimit-remaining` is 0 wait for `x-ratelimit-reset`; else
  wait at least a minute, back off exponentially, then give up. Continuing while limited risks a ban.
- Best practice: **conditional requests** (`If-None-Match`/`If-Modified-Since`) — an authenticated `304` does **not**
  count against the primary limit; avoid concurrency (serial queue per installation); **at least 1 second between
  mutative requests**; follow redirects; use `Link` headers for paging; a 404 can mean "no permission".
- Consequences for the design: A-4's client serialises requests per installation, spaces writes ≥1 s, uses ETags for
  repeated reads (cached per account in the database), honours `retry-after`/reset with a bounded budget inside the
  50-second Vercel limit (beyond it the tool returns `rate_limited` with the reset time in Denver time, never a loop).

### 1.4 Webhooks

- Signed with `X-Hub-Signature-256: sha256=<HMAC-SHA256(secret, body)>` (official library `@octokit/webhooks`
  `verify`). Repository and org hooks have delivery lists, single-delivery reads (request + response), **redelivery**
  (`…/deliveries/{id}/attempts`), `pings` and push `tests` — all in the description. This is what Batch V's delivery
  forwarding replays.

### 1.5 Official client libraries (npm, read 2026-10-10)

`@octokit/core` 7.0.8, `@octokit/plugin-paginate-rest` 16.0.0, `@octokit/plugin-throttling` 11.0.5,
`@octokit/plugin-retry` 8.1.1, `@octokit/auth-app` 8.3.1, `@octokit/graphql` 9.0.5, `@octokit/webhooks` 14.2.0,
`@octokit/openapi-types` 29.0.1, `octokit` 5.0.5 (all-in-one), `libsodium-wrappers` 0.8.4 (secret encryption, the
library GitHub's own guide uses [S9]), `@modelcontextprotocol/sdk` 1.32.1, `@neondatabase/serverless` 1.2.0.
**Decision (A-4):** `@octokit/core` + paginate + throttling + retry + `@octokit/auth-app`, calling `octokit.request('VERB
/path', …)` by route string — the same strings the vendored description uses, so universal tools and hand-built tools go
through one door, and the API version header is set once in `src/github/client.js`. The generated method maps of
`@octokit/rest` are not used (they add a second naming layer and their types track whatever version Octokit generated
from).

## 4. Credentials (playbook step 4)

What GitHub offers [S11][S12][S13][S14]:

| Credential | Lifetime | Scope | Notable limits |
|---|---|---|---|
| **GitHub App installation token** | 1 hour, minted from the App's private key | Fine-grained permissions chosen on the App; only repositories the installation was given; can be **downscoped per token** (subset of repositories and permissions) | Cannot reach personal settings (emails, keys, blocks), user billing, gists writes, codespaces, `transfer`; cannot read notifications |
| **GitHub App user access token** (`ghu_`, refresh `ghr_`) | 8 hours; refresh token 6 months; PKCE (S256) supported | Intersection of the App's permissions and the user's own access | Needed for personal settings, `POST /repos/{o}/{r}/transfer`, `GET /user/installations`, user billing usage, codespaces |
| **Fine-grained personal access token** | Chosen at creation | One resource owner (user or one org); chosen repos and permissions | **Cannot create check runs**, cannot review org token requests (GitHub App only); no notifications; org may require approval |
| **Classic personal access token** | Chosen at creation | Broad OAuth scopes across everything the user can reach | The only credential for **notifications** (and user-owned Projects, migrations); the widest blast radius |

Counted from GitHub's published availability data for API 2026-03-10 (`github/docs` `src/github-apps/data/fpt-2026-03-10/`,
cross-checked against the 1,232 operations): 889 operations accept all three modern credentials; 100 accept App tokens but
not fine-grained tokens (e.g. **check runs and suites**, fine-grained token approvals, most of packages); 92 accept
fine-grained and user tokens but not installation tokens (personal settings, codespaces, gists writes, user billing); 26
accept only a user token (e.g. `transfer`, `GET /user`, `/user/installations`, Marketplace purchases); 109 accept none of
them (classic token or App JWT only: notifications, App management, migrations, Copilot Spaces for users, agent tasks).

**Private GitHub Apps can only be installed on the account that owns them** [S14]. An org-owned private App cannot be
installed on `christcr2012`, where Appliance Desk lives.

**Recommendation (IN-04):** two **private GitHub Apps**, one owned by each account Chris uses (the `Robinson-AI-Systems`
organization and the `christcr2012` personal account), each **registered from the server's setup page through GitHub's
manifest flow** [S12] (Chris clicks "Create GitHub App" on github.com; GitHub hands the App's private key, client secret and
webhook secret straight to the server, which stores them encrypted — nothing to copy, nothing in chat), then installed on its
own account. Plus, once per App, Chris authorizes it as himself on the setup page (OAuth with PKCE) so the server holds an
8-hour user token with a 6-month refresh token for the personal-side operations. Optional and off by default: a classic
token with only the `notifications` scope (IN-11). Reasons: hour-long tokens instead of a long-lived key; per-installation
repository choice; tokens downscoped per connection (a read-only connection literally cannot write); writes show as the
App's bot in GitHub's history; check runs work (Batch V); rate budget grows with repos; the App can be suspended or
uninstalled in one click. Fallback if Chris prefers simplicity: one fine-grained token per account pasted on the setup
page (loses check runs, token approvals and per-connection downscoping; the plan supports it as `kind: 'fine_grained'`).
Classic tokens for general use: not recommended.

## 5. Testing options (playbook step 5)

- **No official GitHub mock** exists (searched 2026-10-10 [S15]). `@octokit/fixtures` (23.1.2) holds recorded scenarios
  for Octokit's own tests — too narrow to be the mock layer. Community mocks (`kiegroup/mock-github`) are unofficial.
- **Decision (A-1/A-4):** a **fake GitHub** in tests (`test/helpers/fake-github.js`): an in-process router behind
  Octokit's `request.fetch` that records every request and **validates it against the vendored OpenAPI description**
  (operation exists for method+path, path/query parameters known, body valid against the operation's request schema
  with `ajv`) and GraphQL documents against the vendored schema (`graphql` `validate`). A CI job `shapes` runs the
  request-shape suite (this repo's equivalent of Stripe's stripe-mock job). Responses come from fixtures whose shape is
  checked against the description's response schema.
- **Real account:** read-only smoke test in close-out (X-2). Writes against a real account only in a **scratch
  organization** Chris creates for this (IN-06), never in his real repositories.

## 6. Service-specific danger → guards (playbook step 6)

| Danger | Guard (design) |
|---|---|
| Force-push or direct push to `main`/a protected branch; deleting it | Production guard (B-2): default branch, any protected branch, any branch with ruleset rules, profile production branches (Appliance Desk `live`); deleting the default branch always refused |
| Merging into the default branch | `pr_merge`: production + confirm, exact head SHA, required checks green at that SHA, `bypass_rules` never sent |
| Releases and tags | Always production |
| Visibility change, delete, transfer, archive, rename, default-branch change | Production + confirm; delete/transfer also destructive; public = access-widening |
| Branch protection and rulesets, Actions settings, org settings | Production + confirm; read-merge-write |
| Actions secrets/variables in production environments or at org level; deployments to production environments; environment protection | Production + confirm; secrets never returned and never accepted as tool arguments |
| Webhooks (repo/org): create, change, redeliver | Production + confirm; signing secrets generated server-side, shown once |
