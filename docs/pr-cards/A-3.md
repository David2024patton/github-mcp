## A-3a — store and primitives

- `src/core/oauth.js` (copied): random tokens, SHA-256 hashing, PKCE S256, redirect validation, IP normalization,
  `evaluateLogin` (5 wrong passphrases in 15 minutes lock the address; counted in `login_attempts`).
- `src/db.js`: `createOAuthClient`, `getOAuthClient`, `createAuthCode`, `consumeAuthCode` (single use, `DELETE … RETURNING`),
  `createAccessToken`, `getAccessToken`, `getTokenByRefreshToken`, `rotateRefreshToken` (one atomic `UPDATE … RETURNING`
  on the same row, same client only), `revokeAccessToken`, `recordLoginAttempt`, `countRecentFailures`,
  `listAccountsForLogin` (login, label, `production_enabled` from `gh_accounts`). Codes and tokens stored hashed only.
- One helper copies every `CONNECTION_FIELDS` value from the issuing row for both grant types — never defaults.
- `test/helpers/fake-db.js` mirrors the same contract.
- Tests: `tests/unit/oauth-core.test.js` (hash, PKCE, redirects, lockout); `tests/db/oauth.test.js` (hashed storage,
  code single use, refresh keeps every setting, refresh only for the same client, two concurrent rotations → one wins,
  revoked/expired refused, lockout counted in Postgres); a test that fails if `oauth_tokens` gains a column named in
  neither `CONNECTION_FIELDS` nor an explicit non-setting list (so a new setting cannot be silently dropped on refresh).
