## Drift check A

| Card assumption | Actual | Kind | Correction / test |
|---|---|---|---|
| Production names are a stored setting | No settings table existed | mechanical | Added `server_settings` (key, JSON value) with `getSetting` / `setSetting`; tested on the fake and on Postgres (shared contract) |
| Turning production on is "two steps" | Needs a place to hold the first step | none | The first step (the tool) creates a single-use `setup_states` row with purpose `enable_production`, 10 minutes; the setup page consumes it. `SETUP_PURPOSES` gained the value |

## Built

- `src/tools/production-guard.js`: `productionReason(ctx, target, {profile, names})` (org/user scope; tags, releases, repository settings; environments by name, reviewers or wait timer; refs by names, project-profile globs, default branch, protected branch, ruleset), `productionNames`, `cleanNames`, `productionEnabledGate` (a production change on a production connection is refused unless the account's switch is on, `by: 'production switch'`).
- `src/tools/gates.js` now returns that gate. `src/tools/server.js`: `github_enable_production` (full profile; always asks; creates the waiting request, changes nothing) and `github_disable_production` (full profile; asks; turns it off at once).
- Setup page: "Turn on production" (confirms the waiting request with the passphrase, logs a change row) and "Names that count as production" (add-only).
- `src/db.js` and fake: `server_settings`, `consumeSetupStateByHint`, `hasPendingSetupState`, `getSetting`, `setSetting`, `setProductionEnabled`.
- Tests: `production-guard` (14), `production-switch` (11), `setup-page` (7 new), `settings-store` and the settings contract on Postgres, updated schema and registry tests.
