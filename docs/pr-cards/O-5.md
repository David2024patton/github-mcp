## Scope and acceptance boundary

Seven predeclared catalog operations: `github_app_list_installations`, `github_app_get_installation`, `github_app_set_installation_repos`, `github_tokenpolicy_list_requests`, `github_tokenpolicy_review_request`, `github_tokenpolicy_list_tokens`, `github_tokenpolicy_revoke_access`.

The owner can inspect which Apps and token holders can access a connected organization, view exact selected repository grants where the user authorizes that metadata, add/remove one selected-repository installation grant, approve/deny one pending fine-grained token request, and revoke one already approved token's organization access. Every write is journalled, confirmation and production guarded, protected resources screened and independently verified. No token bytes or key material appear in arguments, results or logs.

Provider APIs:
- https://docs.github.com/en/rest/orgs/orgs#list-app-installations-for-an-organization
- https://docs.github.com/en/rest/apps/installations
- https://docs.github.com/en/rest/orgs/personal-access-tokens

### Important provider-version limitation

The installation-repository write API is published with different accepted credential types between GitHub.com's REST documentation and Enterprise Cloud documentation. The implementation uses an authorized user grant, checks exact administrator permission and scopes, then either receives a real HTTP 204 with independent GET verification or fails closed with provider refusal. It never fabricates a grant, substitutes a private token, or silently falls back to bypass. A classic token is not requested merely for these controls.
