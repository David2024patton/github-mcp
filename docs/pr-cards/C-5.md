## Drift check

| Assumption | Current code and live measurement | Required approach |
|---|---|---|
| PR read is one GitHub request | `github_pr_get` fetches PR, then GraphQL review, then `ciState` (rules, classic, runs, status serially). Open PR #409 on current live took 3.61 seconds from this connector (one sample; not controlled). | Overlap independent read-only requests while preserving exact-head and all error/unknown rules. |
| Compound status is cheap | `github_workflow_pr_status` reads PR then stack list sequentially; one current-live sample took 7.54 seconds; closed PR #415 read took 2.68 seconds. | Read stack membership concurrently with PR status, retain incomplete/unknown behavior and no writes. |

## Acceptance

1. PR getter performs PR read first (to bind exact base branch/head), then obtains review GraphQL and CI evidence concurrently. Unknown/failed review and missing/failed GitHub checks still never count as merge-ready. Closed PRs do not read CI.
2. CI-state provider reads of classic branch protection, rulesets, head check runs and commit statuses overlap in a bounded four-read fan-out, preserving all required-check union, GitHub-plan exceptions, latest-check ordering, pagination cap, and fail-closed errors. No caching of potentially stale branch/CI/permission state.
3. Compound PR status fetches stack inventory alongside PR evidence using the guarded dispatcher; stack unknown/capped stays unknown. No provider writes or per-profile bypass.
4. A reproducible synthetic benchmark measures the slowest dependent read critical path for a representative PR-check workflow; tests verify bounded concurrency, same outputs, fail-closed errors, and absent calls on closed PRs. Record measured before/after with caveats, not unsupported production speed claims.
5. Source checks, unit, database, browser, RTC, shapes and required exact-head `ci` + `release-policy` green, documentation/review and merge. Leave `live` on its existing scheduled release policy. Synthetic benchmark recorded in CI: CI serial control 100.61 ms vs optimized 25.25 ms (74.9% less); compound status 50.31 ms vs 25.21 ms (49.9% less), five iterations at 25 ms artificial provider wait. These are controlled scheduling measurements, not live latency.
