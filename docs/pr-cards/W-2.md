## Contract and mutations

1. `github_workflow_merge_when_green({owner?,repo,number,expectedHeadSha,confirm?,dryRun?,requestKey?})`: reads PR and actual repository default branch through existing wrapped tools. Refuses changed head, draft/closed/unmergeable, changed base, unknown CI, failing/pending checks, unreadable/unresolved threads and blocking review decision. Delegates ONLY `github_pr_merge` with `method:merge`, the same expected 40-digit SHA and original confirm/production/access/journal gates. Independent post-merge PR readback required for `done:true`.
2. `github_workflow_merge_stack({owner?,repo,prs?|stackNumber?,expectedHeadShas?,confirm?,dryRun?,requestKey?})`: validates bounded unique ordered chain from source/provider; never assumes parent branch equals default. Each invocation either retargets the first unmerged PR via `github_pr_update` or delegates one green exact-head merge via `github_pr_merge`. Returns an exact pending checkpoint and never continues blind after an uncertain write.
3. After a retarget the PR head SHA can stay unchanged while old CI reports green. Read the **complete bounded PR timeline** using the existing `github_issue_list_timeline` tool and compare CI check timestamps with the latest `base_ref_changed` event. Inaccessible/capped histories remain pending; review comments that change `updated_at` alone do not invalidate green checks. A later PR's base is also independently inspected.
4. Merge into any nondefault branch is forbidden in this composite; use existing low-level tool only where explicitly authorized and guarded. Every merge remains production-classified by its delegate; this composed tool cannot elevate a preview connection.
5. Time budget 46 seconds for new mutations; never wait for Actions. No new SQL, approval, checkout, extra permissions or production activation.
