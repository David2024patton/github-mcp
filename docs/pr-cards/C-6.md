# C-6 — One guarded PR creation path and faster exact-head merge preparation

Status: **MERGED (#418; conditioned on green required checks on final documentation head and completed merge)**. Owner-directed continuation after C-3 (#415), C-4 (#416) and C-5 (#417). Approved 2026-10-26: maximize end-to-end repository agent throughput by eliminating unnecessary repeated reads. This source work changes only internal workflows in the existing registered GitHub MCP server; it neither changes user permissions, the guarded writer contract, protected branches nor the daily release schedule.

## Drift check

- `github_workflow_open_pr` (W-1) currently asks for repo metadata and duplicate PR inventory, then delegates to `github_pr_create`, which **rechecks the same repo and PR list** and performs exact branch/duplicate guards itself. For common requests with no labels, the outer reads are redundant.
- `github_workflow_merge_when_green` (W-2) reads exact-head PR and repository default branch sequentially before any write. These are independent and may be read concurrently. The underlying `github_pr_merge` still independently protects exact-head, required CI, review and branch state.
- `github_workflow_merge_stack` fetches chain PRs one by one, up to 15, even though all numbered PR reads are independent. Preserve full ordered chain validation, a maximum of one durable write per invocation and fresh post-retarget checks.

## Acceptance — one complete faster PR conveyor

1. For a feature-branch PR with **no requested labels**, the open workflow delegates immediately to the existing guarded `github_pr_create` writer without duplicated outer repo/PR-list reads. The writer remains the sole authority for target account, default base, duplicate idempotence, branch existence, notification/confirmation and replay; copy its confirmed readback evidence faithfully. If a new PR or existing matching PR is independently verified by the guarded writer, the workflow can report `done:true`. For an unconfirmed/pending outcome, never claim success or try the write twice. Label-bearing workflows retain their existing staged/multi-step guard.
2. The simple exact-head merge workflow launches the verified PR and repository metadata reads together and still refuses bad CI, reviews, drafts, conflicts, wrong base and moved SHA. Merge action and readback remain guarded and sequential.
3. Ordered stack preparation can fetch at most three PR details concurrently, **before** validation and **before** a mutation, preserving original-order chain checks, incomplete/unknown fail-closed behavior, cancellation/time budget and fresh post-retarget CI. No parallel writes, no merged PR before full chain validation.
4. Add deterministic regression and synthetic-delay workflow tests proving fewer redundant read calls, one-write maximum, read fanout upper bound, and unchanged rejection behavior. Record honest before/after *synthetic* results, not generalized production latency claims.
5. Update `docs/OWNER-GUIDE.md`, `docs/TOOL-CATALOG.md`, `docs/DECISIONS.md`, index, tests, owner handoff/status. Exact PR head `ci` and `release-policy` must pass; review and merge only when green; no manual live release.

## Reproducible synthetic evidence

`tests/unit/workflows-fast-lane.test.js` executed `scripts/benchmark-pr-conveyor.mjs` with five iterations and 25 ms fake provider delay per tool: no-label PR open serial control 75.55 ms vs optimized 25.24 ms (66.6% less); exact-head merge 101.34 vs 75.56 ms (25.4% less); six-PR stack inventory 176.08 vs 75.65 ms (57.0% less). This measures scheduling only, not actual production or third-party agent performance. Real writer/dispatcher tests separately verify no duplicate writes, withheld confirmations and readback.
