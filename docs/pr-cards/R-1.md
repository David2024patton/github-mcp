## What it does (plain words)

The owner can issue a service pass with its own limits: preview or production, read-only/everyday/full profile, changes allowed or not, access changes allowed or not, a spend allowance, chosen areas and repositories, a lifetime (up to 30 days; up to a year only for Robinson's Toolkit) and a request limit (default 120 per minute, 1–600). The HTTPS door lists and runs exactly that pass's tools through the same guarded dispatcher. An agent may mint only a preview pass with no spending and no access changes (`github_create_pass`); everything stronger is created on the setup page behind the passphrase.

## Drift check

Checklist A/B (DRIFT-PROTOCOL) done against `origin/main` 77b921e: the legacy read-only pass path (`createRtcPass`, scratch-only, server/meta areas) is unchanged and still the default; the new grant table is additive (`IF NOT EXISTS`); the manifest stays `rtc: 0`; IN-10 is answered (120). Server-area owner tools (`github_create_pass`, revocation, production, spend) are never available to a pass.

## Safety decisions

Defense in depth: database CHECKs, `validateGrant` at issuance, authentication re-validation on every call (account active; production needs production switched on), `passRefusal` in the dispatcher (covers nested calls and `github_call`), `passAccessGate` and the per-pass spend cap in the gates, and credential downscoping to the pass's repositories (a fine-grained token that cannot be narrowed fails closed).
