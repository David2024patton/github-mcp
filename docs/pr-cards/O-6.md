# O-6 — Personal GitHub account operations

Status: IN_PROGRESS until the final exact-head CI/review and merge. **One** predefined batch subsection, O-6, with nine preexisting catalog capabilities; six mutation tools, three read workflows. No invented slices are counted.

## Drift check A — approved design against provider contracts

| Approved assumption | Verified GitHub API behavior | Engineering resolution |
| --- | --- | --- |
| An App installation grant permits personal GitHub account changes | Personal profile, email, SSH/GPG, blocks and invitation endpoints need a **user** grant | Explicit \`U\` credential, exact \`GET /user\` identity, no installation-token fallback; setup-page explanation when not granted |
| All authorized user endpoints have the same permission | GitHub App user permissions distinguish profile, email, keys, blocks and repository invitations | Independent per-area reads, truthful unreadable status; per-operation permission failure is not success |
| Adding an email establishes a verified address immediately | GitHub sends a verification email and may return \`verified: false\` | Mark add as notifying recipient, confirm, read it back, and never claim verification before GitHub reports it |
| Keys can be safely echoed back to the client | GitHub returns public key material (and GPG fields that are not usable as exports) | Validate only public SSH/PGP input; reject private material without echo; expose only ID, fingerprint, timestamps and title |
| Successful delete/accept implies intended remote state | Key, invitation and block operations can race or be eventually consistent | Compare independently read user identity and exact remote object; unconfirmed state remains explicit |
| Replaying a completed delete/accept has the original pending object | Removed keys and resolved invitations disappear from list/read endpoints | Preserve readable absence for idempotency journal; a new request for an absent target never executes a write |
| Profile edits can silently clear unspecified settings | \`PATCH /user\` only updates supplied fields | Reject no-op fieldless changes; send only owner-specified keys; read back all requested fields |
| A public email or added public key has no access implications | Public visibility exposes email; adding SSH/GPG keys creates new authentication/signing authority | Classify access widening, require independent confirmation and protected-resource checks |

## Complete O-6 behavior

\`src/tools/user-account.js\` implements the approved catalog names: \`github_account_get\`, \`github_account_update_profile\`, \`github_account_manage_email\`, \`github_account_list_keys\`, \`github_account_add_key\`, \`github_account_delete_key\`, \`github_account_set_blocked\`, \`github_account_list_invitations\`, and \`github_account_respond_invitation\`.

Scope: Connected account selects the recorded user authorization; the actual personal principal is independently identified by GitHub. Includes bounded verified email and organization/blocked-user inventories, plan/2FA profile metadata, optional explicitly cleared profile fields, non-primary email removal, safe public visibility, three kinds of public key creation/deletion, named blocking decisions, and invitation accept/decline with exact repo readback. Every write uses \`defineGithubWrite\` with user credential, full profile, explicit production and confirmation, request journal, safe preflight, failure handling and readback.
