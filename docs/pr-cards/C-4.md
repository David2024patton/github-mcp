# C-4 — One-call routine writes and efficient independent read batches

Status: **IN PROGRESS**. Approved by the owner 2026-10-26 in follow-up to C-3: make GitHub MCP efficient by design rather than relying on agents to discover speed tactics. Design basis: `docs/designs/BATCH-C.md` (bounded results, meta-tool context). Depends on C-3 (#415). No new permissions, paid services, default-branch writes, automatic production release, schema or secrets.

## Drift check A

| Expectation | Verified code | Change |
|---|---|---|
| Every write requires preview and confirm | `src/core/write.js` allows a routine safe write with `dryRun` omitted and automatically returns `needs_confirmation` for risky classifications; `src/core/meta.js` incorrectly tells every agent to preview first | Correct the instructions and safety marks. One normal call for an already-authorized safe change, optional `dryRun`, human/agent review if `needs_confirmation`. Never bypass the checked write lifecycle. |
| The 10-read batch already executes together | `src/tools/meta.js` loops sequentially over `ctx.callTool`; preflight prevents all writes | Execute independent pre-authorized reads with a fixed maximum in-flight of 3, ordered results and per-read dispatcher authorization, shaping and rate rules intact. |
| Every agent will optimize itself | Agents may re-search or repeatedly preview even when unnecessary | Improve server-provided search/describe guidance; no dependence on custom prompts or agency level. |
| A speedup can be claimed from faster code | No controlled live latency benchmark yet | Synthetic deterministically verified concurrency/ordering and no-write behavior; do not claim real-world elapsed-time improvement without separate measurements. |

## Acceptance — one complete faster everyday gateway

1. `github_search_tools` and `github_describe_tool` accurately explain that ordinary, already authorized writes can be sent once without `dryRun`; `dryRun` remains an optional preview, and any higher-risk operation that returns `needs_confirmation` still needs the authorized confirm follow-up. All profile, target, production, spend, access, notification, idempotency and branch concurrency checks unchanged.
2. `github_batch` starts at most 3 independent reads concurrently out of a maximum of 10, returns results in original requested order with per-item errors, refuses an entire batch containing any write/runner/tool-finder before sending reads, preserves per-read authorization/optional consent and shapes outputs under the same budget. No concurrent writes.
3. Focused deterministic unit tests cover one-call guidance, bounded concurrency, order, partial failures, denial before side effects and existing gateway semantics. No regressions in registry/tool-count/budget/RTC rules. Full exact-head `ci` and `release-policy` checks pass; PR review and merge only after green.
4. Update owner guide, tool catalog, status handoff, index, decision record, and avoid unscheduled deployment. No production traffic or real-provider performance claims before live measurements.
