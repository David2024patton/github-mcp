## #189 — Observability and privacy-safe delivery reads

Build `src/tools/webhooks-read.js` with `github_webhook_list`, `github_webhook_get` and `github_webhook_list_deliveries`. ## #190 — Destructive and outbound webhook delivery controls

Complete native `github_webhook_delete`, `github_webhook_redeliver` and `github_webhook_ping` against exact repo/org hook identities, with source-validated public HTTPS callback destinations for outbound tests. Deletion requires readable existing hook and independently proven 404; replay verifies one additional receipt bound to the original GUID; ping verifies a new ping receipt. Missing asynchronous delivery means honest `unconfirmed`, never an optimistic pass. A saturated preflight delivery inventory refuses an action rather than accepting older arrivals as new. Full-profile + production + confirmation for destructive deletion; delivery changes require explicit confirmation and classify webhook subscription changes as production settings. Request-key/journal replay prevents duplicate sends. Fake-provider and three-door contracts are in `tests/unit/h2-webhooks-actions.test.js`.

No mutation against user or scratch GitHub provider was performed in source implementation. A live account remains PREVIEW/production OFF; real writes need documented explicit gates, source deployment and separate readback. `github_webhook_save` and `github_webhook_rotate_secret` still remain open; they must use service-generated signing secrets, one-time setup-page display and safe callback validation, without exposing values through any tool. No placeholder substitutes for those capabilities. H-2 stays IN_PROGRESS.

## #190 late first-pass security correction

The common `defineWrite` journal stores full `before`/`after` snapshots. Initial H-2 source accidentally allowed the raw GitHub webhook and delivery objects (possibly including signing configurations, request headers or payloads) into those snapshots even though result shaping hid them from the caller. Before merge, the H-2 action client was corrected to allowlist only hook ID, active state, event names, safe HTTPS hostname, delivery ID/GUID/event and redelivery indicator. The full provider response remains transient within the handler only. New tests explicitly inspect recorded change rows and tool responses for leaked fixture strings on delete and replay, including the post-write readback. This is mandatory security acceptance, not optional cosmetic hardening. Re-run exact-head CI after correction; no old-head green result qualifies it.

## Webhook signing-secret lifecycle — implementation checkpoint

The `github_webhook_save` and `github_webhook_rotate_secret` source is implemented in
`src/tools/webhooks-save.js`. Both tools generate independent cryptographic 32-byte
secrets internally, write through the regular production/confirmation/journal gates,
and store only encrypted short-lived, single-use values for owner-passphrase/CSRF-protected
reveal on `/api/github/setup`. Neither secret nor the raw provider response, URL
path/query or webhook delivery payload enters the change journal or MCP response.
Saving an existing webhook explicitly rotates its secret, so the preview warns that
receiver verification must be updated; explicit `rotate_secret` changes only the secret.

`tests/unit/h2-webhooks-save.test.js` covers three write doors, provider readback,
replay, protected targets, secret omission from journal, unsafe callback URLs, TLS
insecurity, missing encryption, and organization scope. Acceptance: exact-head CI and
required reviews before merge; after deployment, separately perform genuinely connected
source-version-verified provider save/rotate/receive/signature/cleanup tests. GitHub masks
signing keys on readback, so independent verification of the key bytes is **not possible**;
prove receiver HMAC verification rather than representing GitHub's mask as proof.

This checkpoint does not activate production or authorize any provider webhook mutation.
