# R-3 — RTC 1 conformance in CI

**Status:** MERGED in #225 as part of the R-1/R-2/R-3 bundle.

## What it does (plain words)

`test/helpers/rtc-fixture.js` serves a tiny fixture registry (one read, ordinary / always-confirm / access-changing writes, one repository read) through this server's REAL HTTPS handler, dispatcher, write layer and gates over a fake database. `tests/unit/rtc-scoped-passes.test.js` runs the vendored upstream runner against it (wired into the `rtc` CI job through `npm run test:rtc`).

## Drift check

Done against `origin/main` 77b921e. The production manifest is untouched (`rtc: 0`); only the fixture server presents `rtc: 1`, so the runner can run.

## Acceptance evidence

Every probe passes (manifest, openapi, catalog, meta, writes, passes, passes.read_only, passes.expired, passes.revoked, safety, budget, oauth.refresh_settings, limits.two_instance) except `reads`. Fault injection (an unprefixed tool) makes `catalog` fail.

## Known limit

The runner's `reads` probe expects a single string longer than 8 KB to be recoverable in full from a result handle. This server's hard 8 KB reply limit makes that impossible by design (long text is paged by offset). It is recorded as a difference, not hidden; the upstream expectation can be revisited with the Hub owner.
